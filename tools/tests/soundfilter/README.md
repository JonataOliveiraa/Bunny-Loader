# Native audio filter

This document and RESULTADOS.md describe the initial step, with synchronous
playback. The evolution into asynchronous dispatch is in
[soundasync](../soundasync/README.md). The check.mjs and the shared fixture
also check the current contract; this step's historical data was kept.

## Analysis

Input: calls to `LegacySoundPlayer.PlaySound`, with a vanilla type or the
SoundStyle marker 1000. Output: vanilla sounds go on to the original; only
the custom marker enters SoundLoader's JS callback.

The C++ bridge's filter runs before `JsLock` and before the arguments are
converted. `arg: 0` identifies the declared `type` parameter, not counting the
receiver. The `sound.mod` mark avoids forwarding to JS high types that are not
the marker. The existing JavaScript guard is still there.

Cases covered: lazy/single installation, vanilla and invalid IDs, different
styles, the original's arguments, chained raw hooks, the direct API, volume,
pitch, pan, distance, silence, instance limits, stop, expiration, cache and
backend failure.

## Design and implementation

| Alternative | Cost | Assessment |
| --- | --- | --- |
| Guard only in JS | One JS entry per vanilla call; constant space | The behavior before the fix, but with unnecessary waits/conversions |
| Native filter + the existing guard | O(1) filter before the lock; fixed-size marks table | Adopted; keeps the path and contract of custom sounds |
| An asynchronous SFX queue | State for requests/streams and its own limit/cancellation | Outside this change; the submitted proposal has regressions documented in the review |

The production change is limited to `SoundLoader.Install`: it registers mark
1000 and passes `{ minType: SoundLoader.ID, arg: 0, marks: 'sound.mod' }` to
the hook. It does not change Kotlin playback nor the order of the music
fades.

## Tests without a device

```powershell
node tools/tests/soundfilter/check.mjs
```

Loads the three production files SoundLoader, SoundStyle and SoundEngine.
Android and the native forwarding are simulated; the results do not measure
QuickJS or FPS. The following integration checks the real bridge.

## Measuring on Android

The runner requires ADB and an emulator with `su 0` and
`run-as com.bunnyloader`. It refuses to prepare the test if there is an active
game session. It uses `BL_SoundFilter_Test` copies of `sda.plr` and
`Pesadelo_Odioso.wld`; adjust those names in the runner for another device.
Do not run it in a session with unsaved progress. The restore checks the
original saves by SHA-256 and the preferences byte by byte, removes only the
temporary package and saves and opens the launcher.

Before building the change, keep the previous APK at
`build/soundfilter/baseline.apk`. Build the filtered APK normally. The full
build is required: the JS classes are embedded in the native library.

```powershell
python tools/tests/soundfilter/device.py prepare
python tools/tests/soundfilter/device.py run --variant baseline --label baseline-1 --apk build/soundfilter/baseline.apk
python tools/tests/soundfilter/device.py run --variant filtered --label filtered-1 --apk app/build/outputs/apk/debug/app-debug.apk
# Repeat with labels baseline-2/3 and filtered-2/3, alternating the APKs.
python tools/tests/soundfilter/device.py restore
python tools/tests/soundfilter/analyze.py build/soundfilter/127.0.0.1-16384 --out build/soundfilter/summary.json
```

Always run restore, including after a failed round. The backup files and logs
live in `build/soundfilter/<device>/`.

The WAV tones and the texture are generated by the runner, without depending
on another mod's audio. Each round loads the same initial character/world,
enables only the fixture and uses four 200 ms effects, a looping track and 32
temporary NPCs with no movement/damage. The NPCs exercise registration, the AI
bridge and music selection; they do not simulate the complex AI of a Split
boss.

After warming up, each phase discards 60 updates and measures 180 batches:

| Phase | Requests per update |
| --- | --- |
| vanilla | 48 vanilla requests through the native API |
| mixed | 48 vanilla + 12 custom markers through the native API |
| custom-marker | 12 custom markers through the native API |
| custom-direct | 12 requests through the JS API SoundEngine.PlaySound |

The custom sound goes through the normal path, with MaxInstances 0. It is a
deliberate saturation test, reaching 720 custom requests/s at 60 updates/s.
SoundPool's 32-stream limit still applies. The fixture also checks
ReplaceOldest, IgnoreNew, distance, expiration, actually using an item with a
custom UseSound, music and removing the NPCs.

`bl.hookStats()` measures calls, JS entries and callback time without the
original. **The time includes JNI calls and waiting on the Android backend; it
is not pure QuickJS CPU.** The direct JS API does not go through the Legacy
hook, but SoundLoader.Play still runs in JS. Zero on that hook's counter does
not mean there is no JS work on the direct path.

The batch measures how long it takes to fire the requests. DoUpdate measures
the complete update and DoDraw measures intervals between draws. The game can
run several updates between draws; so 180 updates are not necessarily 180
rendered frames. The summary uses the median of three rounds and also keeps
the range of results of each counter.

Emulator measurements do not guarantee FPS on phones nor reproduce every
weapon, NPC or file of Split. See `RESULTADOS.md` for the data and limits of
the recorded run.

## Optional backend profile

Add `--profile` to the `run` command, using different labels, like
`profile-baseline` and `profile-filtered`. That option instruments only the
fixture: it measures the time inside `bl.sounds.play/stop`, counts the
backend's zero returns and adds the `custom-ignore` phase, with the same 12
requests per update and MaxInstances 1/IgnoreNew. It does not change the
Kotlin nor the mods' defaults. Run restore when done.

The wrapper adds clock reads. That is why these rounds are a separate
diagnosis and do not go into the main A/B median. The measured interval
includes JNI, dispatch and waiting on Android; it does not by itself identify
which internal SoundPool operation consumes CPU or blocks.
