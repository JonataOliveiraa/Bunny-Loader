# Architecture decision: how to put Bunny Loader inside Terraria

Status: **open**. Written after Phase 1 ran into PairIP.
Technical reference: [UNITY-HOSTING.md](UNITY-HOSTING.md).

---

## 1. The problem, measured

The project's goal was never to host `UnityPlayer` — it was to **put
`libbunny.so` inside the game's process** in order to hook the methods
generated by IL2CPP. Hosting was just the chosen means.

That means hit a wall. What is proven on the device:

| Fact | Evidence |
|---|---|
| The APK uses PairIP | `application:name = com.pairip.application.Application` |
| The app's string constants are encrypted | `uk.co.drstudios.lvl.yh.sHQPfQqKk`: 13 `static String` fields, **zero methods** |
| Without them, Unity breaks | `getNaturalOrientation` reads `sHQPfQqKk.pPb` (should be `"window"`) → `getSystemService(null)` → NPE |
| Triggering `StartupLauncher` directly does not solve it | Probe before and after: `null`. Everything "ok", nothing populated, in the same millisecond |
| Because the dex's `invoke` is a stub | `VMRunner.invoke` starts with `const/4 v0, 0; return-object v0`; real body at offset 0002, unreachable |

The conclusion: **`libpairipcore.so` rewrites that method in memory, and only
does so when initialized through the app's legitimate boot path.** Loading the
lib is not enough.

---

## 2. The paths

### A. Host in our process (the current design)

Keep going as is and make our process pass as legitimate to
`libpairipcore.so`.

What remains to be found out: what exactly it checks. Likely candidates are
the package name, the APK signature and whether the real `Application` ran.
Each of those is one item to work around, and none is mapped yet.

- **Root:** not needed
- **Distribution:** the cleanest — our APK alone, the user uses their own copy
- **Fragility:** high. It is an arms race against a protection Google updates;
  every game update can break it
- **Effort:** unknown, and that is the problem — it could be an afternoon or
  it could never end

### B. Launch the game and inject into its process

The launcher starts Terraria normally. Its `Application` runs, PairIP
initializes, the strings get populated, everything works as designed. Then we
inject `libbunny.so` into that process.

The Java layer problem **disappears completely** — we stop fighting PairIP and
start living with it.

- **Root:** **yes**, for injecting into someone else's process (ptrace, or a
  Zygisk-style module)
- **Distribution:** the APK is free, but only works on a rooted device. For
  mobile Terraria that cuts off the overwhelming majority of the audience
- **Fragility:** low on the Java side. The native part (offsets) is already
  resolved at runtime and validated by `GameRefs`
- **Effort:** moderate and predictable

### C. Repackaging the APK

**Beware of a misunderstanding:** repackaging **is not removing PairIP**. The
strings are encrypted and only `libpairipcore.so` decrypts them — without
PairIP the app does not work. Repackaging means **keeping PairIP intact** and
only adding our `libbunny.so` plus a hook that loads it.

But when re-signing the APK, `SignatureCheck` (which compares against the
embedded signature) starts failing. It lives in
`Application.attachBaseContext` and is **not** VM-protected, so it can be
neutralized. What remains unknown is whether `libpairipcore.so` does its own
check internally.

- **Root:** not needed
- **Distribution:** here is the delicate point. The modified APK is an altered
  copy of a paid game — **it cannot be distributed**. What gets distributed is
  the *tool* that applies the patch, and each user applies it to their own
  copy. That is viable and a known pattern, but it changes the product: Bunny
  Loader would stop being just an app and would also have a patcher
- **Side effects:** a different signature from the Play Store (loses automatic
  updates, can conflict with the original install), and Play Integrity
  breaks — irrelevant offline, relevant if the game checks something online
- **Fragility:** medium. Redo the patch on every game update
- **Effort:** high

### D. Develop first against a version without PairIP

It is not a final path, it is a way to reduce risk. Older versions of mobile
Terraria predate PairIP. Running the whole pipeline on them (Phases 1 to 4)
proves the architecture end to end, and PairIP becomes an isolated problem,
tackled later with the rest already working.

- **Cost:** one more dump, and the offsets change between versions (`GameRefs`
  already refuses to start if something does not resolve, so this is
  detected, not silent)
- **Risk:** solving the easy part and finding out late that the hard part has
  no solution

## 3. Comparison

| | A. Host | B. Launch + inject | C. Repackaging | D. Old version |
|---|---|---|---|---|
| Needs root | no | **yes** | no | no |
| Reachable audience | everyone | rooted only | everyone | everyone |
| Distributes what | only the app | only the app | app + patcher | only the app |
| Redistributes the game | no | no | **no** (local patch) | no |
| Effort | unknown | moderate | high | low |
| Fragility per update | high | low | medium | — |
| Known blocker | yes | none | signature | none |

## 4. What holds regardless of the choice

Nothing that was done is lost:

- **All of Phase 0** — `tools/dump.sh`, `tools/dumpgrep.sh`, the validated
  dump, the checked offsets. That was always about the native side
- **`GameRefs`** and the discipline of resolving everything at runtime with
  validation
- **The native core** (`libbunny.so`): LibWatcher, HookManager, Il2CppApi,
  ScriptEngine. They all operate inside the game's process, no matter how we
  got there
- **The diagnosis** — without it we would still be staring at `null`

What is specific to path A is the hosting layer: `GameEnvironment`,
`UnityHost`, the Context overrides in `GameActivity`, `PairipBootstrap`.

---

## 5. What I do not know

Honesty about the limits of what is established:

- **How other launchers do it.** There are launchers that run without root and
  load mods into Terraria. I did not investigate, and I will not guess
- **What `libpairipcore.so` checks.** Without that, the effort of path A is an
  unknown number
- **Whether it does its own signature check**, which affects path C
- **Whether old versions of Terraria really have no PairIP** — plausible given
  the timing, not checked

---

## 6. Recommendation

**B to unblock now, with C as the distribution path later.**

The reasoning: the project's value is in the native core and the mod API, and
none of that has been tested yet. Path B gets there fast and with predictable
risk, because it stops fighting PairIP. With root on MuMu, Phases 2, 3 and 4
can be gone through entirely and JS mods can be running.

Only then does the distribution question become mature — and then path C
solves the reach, with the core already proven and the only unknown being the
signature.

Path A is the only one that delivers everything at once, and that is exactly
why I distrust it: the effort is unknown and maintenance is a race against
updates we do not control.

**If reach without root is a non-negotiable product requirement**, then the
order flips and C becomes the main path right away — worth saying now,
because it changes what to build next.

# DECISION MADE: path B (launch + inject)

Chosen to unblock Phases 2-4. Distribution without root is left for later
(probably path C).

## Injection mechanism: the `wrap.<package>` property, not ptrace

Measured on MuMu (device emulator-5554):

| Item | Value |
|---|---|
| SELinux | Permissive |
| root (`su`) | works |
| `ro.debuggable` | 0 (user build) |
| Magisk/Zygisk | absent |
| `setprop wrap.com.and.games505.TerrariaPaid ...` | accepted and reads back |

`wrap.<package>` is a standard Android startup feature (the same as the
profiling/debug `wrap.sh`). With it Zygote launches the app under a wrapper,
which allows `LD_PRELOAD` of `libbunny.so` into the game's own process.

Why not ptrace: under MuMu's ARM→x86 translation, tampering with a process
through ptrace is fragile (the same reason native hooks need real ARM).
`wrap.` operates at the Zygote startup level, not instruction by instruction,
so it does not depend on the translator.

## What this changes in the code already written

- **Out:** the hosting layer: `GameEnvironment`, `UnityHost`, the Context
  overrides in `GameActivity`, `PairipBootstrap`. I am not deleting them yet —
  they stay as a reference until the new path is up
- **Stays:** everything in the native core and Phase 0
- **In:** the launcher now (1) sets `wrap.` through root, (2) starts the
  game's real Activity, (3) `LibWatcher` already registers the pending
  `il2cpp_init` hook as soon as `libbunny.so` is preloaded

## New boot sequence

```
LauncherActivity (our process, no root for the UI)
  └─ "Play"
       ├─ via root: setprop wrap.<pkg> = LD_PRELOAD=.../libbunny.so
       ├─ via root: am start com.and.games505.TerrariaPaid/.UnityPlayerActivity
       └─ Zygote starts the game with libbunny.so preloaded
             ├─ the game's Application runs → PairIP initializes → strings OK
             ├─ libbunny's constructor (or JNI_OnLoad) → LibWatcher
             │     └─ pending hook on il2cpp_init (ShadowHook)
             └─ Unity loads libil2cpp.so → il2cpp_init → runtime::boot()
```

The elegant point: `libbunny.so` is loaded **before** `libil2cpp.so` because
`LD_PRELOAD` happens at exec. ShadowHook's pending hook, which is already in
the code, was made exactly for this.

## Open items of this turn

- Where `libbunny.so` runs the bootstrap: it needs an entry point at the lib's
  load (a `__attribute__((constructor))` or `JNI_OnLoad`), since there is no
  longer the Java `NativeBridge.init` calling `installWatcher`
- How to pass the config (modsDir, etc.) to a process that is not ours:
  probably a file in an agreed location (e.g. `/data/local/tmp/bunny/`) that
  the lib reads at load
- Copying `libbunny.so` to a path the game's process can read

# RESULT: repackaging works; the hook needs real ARM

Measured on MuMu with the repackaged APK (libmain.so with NEEDED libbunny.so):

```
BunnyLoader: libbunny carregada no processo do jogo (config=sim, versao alvo 301543)
BunnyLoader: Falha ao registrar hook de il2cpp_init: Linker with an unsupported architecture
IL2CPP: JNI_OnLoad
Unity: 2021.3.56f2 ... CPU 'arm64-v8a' ... Backend 'il2cpp'
IL2CPP: Locale pt-PT
shadowhook_tag: shadowhook init(mode: UNIQUE), return: 0, real-init: yes
```

In the game's process: libbunny (3), libshadowhook (3), libil2cpp (6) mapped;
the game reaches the menu.

## Proven
- Injection through repackaging (DT_NEEDED in libmain.so) puts our lib into
  the game's process — our constructor runs.
- PairIP worked around: running inside the game's process makes the strings
  get decrypted normally. Re-signing with a dev key did NOT abort the boot (no
  SignatureTamperedException). That is, in this build PairIP's signature check
  does not bring down the repackaged app.
- No dex changed.

## Remaining blocker (the emulator's, not the design's)
`shadowhook_init` returns 0, but registering the hook fails with "Linker with
an unsupported architecture". Under houdini (MuMu's ARM->x86 translation),
ShadowHook does not recognize the linker to do the inline hook. This is
exactly the warning repeated since Phase 0: **native hooks need real ARM.**

## Next step
The injection layer is ready and reproducible (tools/repack.py). The hook
engine can only be validated on real ARM — an ARM Android device (ideally with
root/Magisk to go back to the clean path B, but repackaging also runs without
root) or an ARM host. Everything up to il2cpp_init is done on the emulator.

# PHASE 3a VALIDATED on the emulator: the resolution layer works

The probe (boot/Probe.cpp) ran in the game's process and resolved everything
by name, with the offsets matching the 1.4.5.6.4 dump:

```
sonda: il2cpp pronto; carregando API
GameRefs ok | Entity.velocity=0x1C (esp 0x1C) Projectile.type=0x64 (esp 0x64) active=0x49 (esp 0x49)
sonda: RESOLUCAO OK — camada de bind validada no processo do jogo
```

Proven under houdini (emulator):
- Calls to the IL2CPP API (il2cpp_*) work translated.
- Api::load() finds Assembly-CSharp.dll + mscorlib.dll.
- resolveGameRefs() resolves classes/fields/methods -> correct offsets.

Critical detail: calling il2cpp_domain_get() DURING il2cpp_init crashes
(SIGSEGV). The probe waits for the game to settle (10s) before touching the
API. The hook path (ARM) does not have that problem because it only runs after
init.

Only the inline hook is missing, and it is ARM-only. Work order from here:
- Real ARM: install the watcher (ShadowHook) and run runtime::boot() for real
  -> Projectile.AI/SetDefaults hooked -> Phase 4 (QuickJS).
- On the emulator: everything that does not depend on the hook can move
  ahead — the QuickJS bindings, content registration, and reading/writing game
  state through the probe.

# CORRECTION: the hook WORKS on the emulator (by address)

The user's observation (another mod launcher runs on MuMu) was right and
overturned the earlier conclusion of "hooks only on real ARM". Measured:

```
hooktest: Projectile.SetDefaults hookado (por endereco)
hooktest: Main.DoUpdate hookado — aguardando disparo
>>> HOOK Main.DoUpdate DISPAROU (frame 0) — hook funciona sob houdini!
```

The game stays alive, our code runs every frame and calls the original.

## What really fails under houdini
Only the PENDING mode by name: `shadowhook_hook_sym_name("libil2cpp.so", ...)`,
which inspects the x86 linker -> error 35. `shadowhook_init` itself passes.

## What works under houdini
`shadowhook_hook_func_addr` on an ALREADY loaded method: it rewrites the ARM
function's prologue (houdini translates it), without touching the linker.
Since the inline hook patches the target's prologue, ALL callers are
redirected — including the direct calls compiled by AOT (it is not a pointer
swap).

## Consequence for the design
We do not need to hook il2cpp_init. The boot trigger becomes "wait for il2cpp
to be ready" (as the probe already does) and then install the runtime hooks by
address. The same code runs on the emulator AND on real ARM. The A/B/C
distribution paths still hold; the whole development (Phases 3 and 4) is
unblocked on MuMu, without root and without ARM.
